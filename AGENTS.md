# AGENTS.md

`nullscan` is a Rust workspace for a TypeScript static analyzer: a reusable core crate, a shared workspace crate, a CLI, and an LSP server. Read `README.md` for usage and `FINDINGS.md` for the full tree-sitter investigation notes.

## Commands

```sh
cargo test --workspace                       # full suite (~35s, 350 tests)
cargo test -p nullscan-core flags_explicit_any   # one test by name
cargo run -p nullscan -- path/to/src/         # analyze files/dirs
cargo run -p nullscan -- src/ --format sarif
cargo run -p nullscan -- src/ --format json
cargo run -p nullscan -- src/ --config path/to/nullscan.toml
pnpm --dir editors/vscode install            # VS Code extension (own package.json)
pnpm --dir editors/vscode typecheck
pnpm --dir editors/vscode test
pnpm --dir editors/vscode build              # bundle dist/extension.js
NULLSCAN_LSP_PATH=$(pwd)/target/debug/nullscan-lsp pnpm --dir editors/vscode test:integration
pnpm --dir editors/vscode package --no-dependencies --out /tmp/nullscan.vsix
./scripts/check-coupling.sh                  # cargo tree guards, same as CI
./scripts/check-version.sh v0.1.0            # tag vs Cargo.toml + package.json
```

There is no rustfmt/clippy config or pre-commit hook; `cargo test --workspace` is the local
verification step. Edition 2024 requires a recent toolchain (tested on 1.98).

CI lives in `.github/workflows/ci.yml` (push to `main` and pull requests): `cargo test
--workspace`, the `cargo tree` coupling guards (`scripts/check-coupling.sh`), the extension
typecheck/unit tests/build, and the real VS Code integration test under `xvfb-run`.
Releases are tag-driven through `.github/workflows/release.yml`, which runs
`scripts/check-version.sh <tag>` in a `verify` job before building anything.

The version is single-sourced: Rust members use `version.workspace = true` and read
`[workspace.package].version` from `Cargo.toml`; the internal path dependencies carry no
`version`. `editors/vscode/package.json` must be bumped to the same value, and
`scripts/check-version.sh <tag>` (or `v<version>`) exits `1` when any of the three
disagrees. Release steps, asset names and re-run instructions live in `RELEASING.md`; the
shipped scope per version is in `CHANGELOG.md`.

## Commits

- Use Conventional Commits: `type(scope): summary`, with types `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.
- Scope names the affected area, for example `feat(rules): add no-eval` or `fix(cli): keep output order deterministic`.
- Summary: English, imperative, lowercase after the colon, <= 72 chars, no trailing period. Body explains why, wrapped at 72.
- One logical change per commit; keep refactors separate from behavior changes. Land a rule together with its fixture pair and its `RULES.md` row in a single commit.
- Commits before this convention use a free-form style; do not rewrite history.

## Code style

- All identifiers, comments, doc comments, log/error messages and test names are in English.
- Keep functions atomic: one job, roughly <= 40 lines, <= 4 parameters, nesting <= 3. Extract helpers rather than growing `run()` functions.
- Group code by domain: one module per rule under `lang/typescript/rules/`, and shared helpers in the module that owns them (`rule.rs`, `scope.rs`, `control_flow.rs`) instead of a generic `utils` module.

## Layout and flow

- `nullscan-core/` — tree-sitter parsing, the rule registry, per-file rules, cognitive complexity, cross-file duplication. No `serde` in this crate; `Config` is a plain struct.
- `nullscan-core/src/text.rs` — source-position helpers shared by consumers that speak UTF-16, chiefly `byte_col_to_utf16(line, byte_col)`. It converts a 0-based byte column on one line into a 0-based UTF-16 code-unit column, clamping out-of-range or mid-character columns.
- `nullscan-core/src/suppression.rs` — applies `// nullscan-ignore-next-line [rules]`, `// nullscan-ignore-line [rules]` and their `/* */` forms to file-scoped diagnostics. Only real tree-sitter `comment` nodes count (markers in strings/JSX text are inert), the marker must start the comment and end on a word boundary, no list means every rule, and stacked markers on one line combine. `analyze` calls it after collecting diagnostics; project-scoped `duplicate-code` is not affected.
- `Diagnostic` (in `nullscan-core/src/lib.rs`) carries `rule`, `severity`, `line`/`column`, `end_line`/`end_column` and `message`. Positions are 1-based byte positions; `Severity` is ordered `Error < Warning < Info` and exposes `as_str()` for text, SARIF and JSON. `rule::severity_of(rule_id)` resolves a registry id to its level and is re-exported from the crate root.
- `nullscan-core/src/rule.rs` — **single source of truth** for rule metadata: `RuleMeta` (id, description, title, why, severity), `RuleScope`, `Rule`, `FileContext`, and the `RULES` registry (including the project-scoped `duplicate-code`). `title` is the short sentence-case name, `why` the one-sentence rationale, and both feed the LSP catalog, hover and `codeDescription` links.
- `RULES.md` — human-facing catalog, one row per registry rule: category, closest SonarJS/ESLint equivalent, and implementation status. The first cell of every row starts with `<a id="<rule-id>"></a>`, so `RULES.md#<rule-id>` is a stable GitHub anchor used by the LSP; `nullscan-core/tests/rules.rs` fails when a registry rule has no anchor. Update it when adding a rule.
- `nullscan-core/tests/rules.rs` + `nullscan-core/tests/fixtures/<rule-id>/` — fixture-based regression harness. It discovers fixture directories dynamically and checks `valid.ts|tsx` (zero diagnostics for that rule) and `invalid.ts|tsx` (at least one). Other rules may fire on a fixture; only the rule named by the directory is asserted. Project-scoped rules are skipped.
- `nullscan-core/src/scope.rs` — owned per-file lexical scope graph (`ScopeGraph`): module/function/block/catch/class/loop/switch scopes, binding kinds, and references with read/write counts. `Reference` also records `is_type_position` (identifier is a `type_identifier` or sits under a type-context ancestor), which `no-use-before-define` skips; class heritage is visited in the enclosing scope because JS evaluates `extends` there. No tree-sitter `Node` values are stored. Built lazily by `analyze` only when an enabled file rule has `requires_scope: true`.
- `nullscan-core/src/control_flow.rs` — small reusable statement helpers, deliberately not a CFG: `statement_terminates`, `last_statement`/`last_executable_statement`, `statements`, `body_statements`, `is_function_like`, `is_loop`, and `collect_returns` (skipping nested functions). The reachability/dataflow rules share these instead of duplicating tree walks; termination coverage is limited to return/throw/break/continue, terminating blocks, and `if`/`else`. Unit tests for the helpers live in the module.
- `nullscan-core/src/lang/typescript/rules/` — one module per per-file rule; each exposes `pub fn run(&FileContext) -> Vec<Diagnostic>`. Shared query helper in `query.rs`. Scope-dependent rules read `ctx.scopes` and return early when it is `None`.
- `nullscan-core/src/cognitive_complexity.rs` — the cognitive-complexity metric, kept at the crate root; the TypeScript rule module only wraps it.
- `nullscan-core/src/duplication.rs` — copy-paste detection (jscpd/PMD CPD style): tokenize, hash sliding windows, extend each match to its maximal run. `find_duplicates` returns `DuplicateReport { duplicates, stats }` from `DuplicateOptions { min_tokens, compare_markup }`; `compare_markup: false` (the default, from `Config::duplicates_compare_markup`) drops JSX markup — tags, attributes, attribute strings, `jsx_text`, static JSX and `<svg>` subtrees — and keeps only the logic inside `{...}` expressions, while `true` tokenizes everything. `Duplicate` carries `line_count`; `DuplicationStats` reports `duplicated_lines`, `total_lines` (LOC: non-empty and not entirely comment, derived from the same parse), `duplicated_blocks`, `duplicated_files`, `largest_block_lines` and `density()` (percentage of duplicated LOC, rounded to one decimal, union per file). Unit tests here cover identical blocks, distinct files, one-report-per-run, short snippets, self-overlap, SVG and static-JSX markup ignored by default, markup counted when enabled, expression logic still flagged, LOC/comment edge cases, overlapping-clone unions and density rounding.
- `nullscan-workspace/` — everything that must behave identically in the CLI and the editor integration. `walk.rs` owns `SKIPPED_DIRS` and the recursive file collector (sorted/deduplicated files plus warnings); `config.rs` owns `nullscan.toml` loading and validation, including `[files].ignore`, `[duplicates].ignore`, `[duplicates].compare-markup` (default `false`, applied to `Config::duplicates_compare_markup`) and `[rules.no-duplicate-string].ignore` (unquoted literal contents, applied to `Config::duplicate_string_ignore`); wrong TOML types are config errors; `ignore.rs` owns the `PathFilter` glob matcher (`*`, `?`, `**`, trailing `/`, segment vs full-relative patterns, absolute patterns, no negation); `scan.rs` owns reading + parallel analysis + duplicate detection (`find_duplicates` with `DuplicateOptions` built from `duplicate_code_min_tokens` and `duplicates_compare_markup`) + the `maxDiagnostics` cap and returns a `ScanReport`; `json.rs` owns the serializable `Summary`/JSON contract (0-based UTF-16 ranges). It must stay free of `clap` and any LSP crate, and it must not depend on `nullscan-lsp`.
- `nullscan/` — thin CLI: `clap` argument parsing (`--format`, `--config`, `--max-diagnostics`, `--version`), calls `nullscan_workspace::scan`, then text/SARIF/JSON formatting and exit codes. No walking, config parsing or analysis orchestration lives here.
- `nullscan-lsp/` — `bin nullscan-lsp`: the stdio JSON-RPC transport and hand-written argument parsing (`--stdio`, `--version`, optional `--config <path>`), the open-document store, custom request handlers and summary cache (`server.rs`), the workspace-scan worker job (`requests.rs`), the serializable rule catalog for `nullscan/rules` (`rules.rs`), client settings (`settings.rs`), the analyze-on-type debouncer (`debounce.rs`), outgoing notifications shared with the worker (`messages.rs`), core→LSP diagnostic mapping with UTF-16 ranges and `codeDescription` links (`convert.rs`), diagnostics-under-the-cursor Markdown (`hover.rs`), the disable-rule and suppress-line quick fixes (`code_action.rs`), `nullscan.toml` edits that preserve formatting (`config_edit.rs`), and `file:` URI↔path conversion (`uri.rs`). It owns the LSP transport and buffer overlays; `nullscan` must never depend on it and it must not depend on `nullscan` or `clap`.
- `editors/vscode/` — thin VS Code language client (`vscode-languageclient`), with its own `package.json` and lockfile and no Cargo workspace membership. `src/binary.ts` resolves the server (`nullscan.path` → bundled `bin/<platform>-<arch>/` → downloaded cache → `PATH`) and owns the `<platform>-<arch>` → release-triple map, `src/download.ts` downloads and verifies it, `src/settings.ts` reads the `nullscan` section, `src/configPath.ts` resolves `nullscan.configPath` without touching the VS Code API, `src/summary.ts` owns the status bar and custom-request wrappers, `src/aggregate.ts` turns `languages.getDiagnostics()` into issues and sorted rule/file groups, `src/rules.ts` indexes the `nullscan/rules` catalog and falls back to the rule id and the generic `RULES.md` page, `src/duplication.ts` formats the duplication card (`density`, bar, lines, blocks, files, largest block), `src/tree.ts` owns the **By Rule** / **By File** tree views, `src/webview.ts` the single summary panel, and `src/extension.ts` wires activation, commands and the client lifecycle. Both UIs read the diagnostics VS Code already holds (filtered to `source: "nullscan"`), never an issue list from the server; only the rule catalog comes from it, fetched right after `client.start()` and again on restart, so the trees show the human title with the id as description and the summary panel shows it as a secondary line. `nullscan.showRuleDocumentation` opens the selected rule's `docs_url`, from a rule node directly or from a palette QuickPick built from the catalog. It holds no analysis logic and must never shell out to the `nullscan` CLI.
- `editors/vscode/test/integration/extension.test.ts` runs in a real VS Code instance through `@vscode/test-electron`; `.vscode-test.mjs` bundles it to `out/` (excluded from the VSIX) and opens `test/fixtures/workspace`. The runner must set `NULLSCAN_LSP_PATH` to an absolute `nullscan-lsp` build; the suite sets `nullscan.path` from it, opens `src/app.ts` and waits up to 10 s for a `no-console` diagnostic with `source: "nullscan"`. `vitest` ignores `test/integration/**`.
- `editors/vscode` downloads the server only when `nullscan.path` is empty and no bundled binary exists. Releases publish raw binaries, no archives: `nullscan-lsp-<triple>` (`.exe` on Windows) for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin` and `x86_64-pc-windows-msvc`, plus `checksums.txt` with one `<sha256>  <asset>` line per file, under `https://github.com/bytezer/nullscan/releases/download/v<version>/`. `src/download.ts` fetches `checksums.txt`, streams the asset to a temp file next to `<globalStorage>/server/<version>/<asset>` while hashing, compares SHA-256, sets mode `0755` on Unix, atomically renames, and runs `--version` (semver core, so `-beta.N` is ignored) before accepting it. A cache entry is reused only when its hash matches; a mismatch deletes it and downloads again, and a failed verification deletes the binary. Redirects are followed manually with `node:https`/`node:http`, `http.proxy`/`http.proxyStrictSSL` go through `https-proxy-agent`, and production URLs must be `https:`. The only non-`https:` override is `NULLSCAN_DOWNLOAD_BASE_URL`, for tests. The `nullscan.redownloadServer` command deletes the cache entry and downloads again.
- `textDocument/codeAction` is advertised with `codeActionKinds: ["quickfix"]` and answered with one `Disable <rule> in nullscan.toml` action per distinct rule (first-seen order). Candidates come from `context.diagnostics` when the client sends any, otherwise from the diagnostics published for that URI (`file` + `duplicates`) that intersect the requested range, so a cursor-only request still works; diagnostics without a string `code` are skipped and each action carries the diagnostic that triggered it. The target config is the nearest workspace folder's `nullscan.toml` via `nullscan_workspace::config::load_in_dir` (`LoadedConfig.path`, else `folder/nullscan.toml`), or the document's own directory without a workspace folder; its text is the open buffer when that URI is open, else the file on disk, and a missing file means empty content.
- The same request also offers `Suppress <rule> on the next line`, a single insertion on the document itself: it inserts `<indent>// nullscan-ignore-next-line <rule>` at the start of the diagnostic's line using that line's indentation and the document's newline style, or appends `, <rule>` to an existing `//`/`/* */` marker on the previous line. No action is offered when the previous marker has no rule list or already names the rule.
- Files matched by `[files].ignore` get an empty diagnostics list even when opened: `Server::config_for` returns the full `LoadedConfig` and `analyze_document` checks `ignore.matches(path)`. Workspace scans already exclude them in `walk`.
- The code-action edit is never applied server-side. It always replaces the whole config document (`DocumentChanges::Operations` with version `null` for disk files; range 0:0 to the end of the current content, which covers a trailing newline) with `config_edit::add_disabled_rule`'s output, which appends the rule to `[rules].disabled` while keeping comments and unrelated keys byte-identical and is idempotent; a `rules` or `disabled` value of the wrong TOML type yields no action and one `window/logMessage` warning. A `CreateFile` operation precedes the edit when the config is neither on disk nor open.
- Diagnostics are pushed on `didOpen`/`didSave` (each gated by its setting) and, when `analyzeOnType` is on, after the debounce; full text sync, `positionEncoding: utf-16`, `source: "nullscan"` and the rule id as `code`. Each diagnostic also carries `codeDescription.href` = `https://github.com/bytezer/nullscan/blob/main/RULES.md#<rule-id>` when that URL parses (never a panic otherwise), so editors can open the rule docs. `didChange` always refreshes the stored buffer and only queues debounced work. Every log line goes to stderr because stdout is the JSON-RPC channel.
- Published state is two groups per URI (`Published { file, duplicates }`): `file` is refreshed by open/save/type/scan, `duplicates` by the last workspace scan. Every publishing path sends `file + duplicates` in one `publishDiagnostics`; `didChange`/`didSave` drop only `duplicates` because their ranges describe the scanned text, and the next workspace scan restores them. `didClose` clears both groups.
- `duplicate-code` is emitted on both sides of every `Duplicate`: each file gets its own diagnostic plus one `relatedInformation` entry pointing at the other file and range. The range spans the duplicate's lines (character 0 to the UTF-16 length of the end line), with the registry severity and `source: "nullscan"`. The message is `duplicated block of <N> lines (<T> tokens), also found at <file>:<start>-<end>`, using the side's own span.
- `textDocument/hover` is advertised and answered from the published groups: the diagnostic whose range contains the position (start inclusive, end exclusive) becomes Markdown with `**<title>** (\`<id>\`) — <Error|Warning|Info>`, the registry `why`, the concrete message and a `[More](https://github.com/bytezer/nullscan/blob/main/RULES.md#<id>)` link; a code that is not in `RULES` keeps the older `**rule** — severity` plus description shape. No diagnostic means a `null` result.
- `nullscan-lsp/src/settings.rs` owns the client settings (`analyzeOnOpen`, `analyzeOnSave`, `analyzeOnType`, `includeDuplicates`, `maxDiagnostics`), parsed from `initializationOptions` and refreshed by `workspace/didChangeConfiguration`. Both `{ "nullscan": { ... } }` and flat payloads are accepted: nested keys win over flat ones, unknown keys are ignored, a wrong type keeps the current/default value, and an update only touches the keys it names. `maxDiagnostics` replaces the old hardcoded scan cap, and `includeDuplicates: false` adds `duplicate-code` to each scan config's `disabled_rules` without changing the workspace API.
- Analyze-on-type is debounced in `nullscan-lsp/src/debounce.rs`: `didChange` queues the URI on a dedicated thread that waits 250 ms of quiet (`DEBOUNCE_INTERVAL`; latest edit per URI wins, the interval is injectable for tests) and hands it back so the dispatch loop `select!`s on `debounce_results()` alongside client messages and job results. `Server::analyze_debounced` re-analyzes the current buffer only when the document is still open and the setting is still on, which is how `didClose` drops pending work.
- `workspace/didChangeWatchedFiles` is the only config-watch input; the client owns watcher registration and the server just reacts. A change whose file name is `nullscan.toml` republishes every open document under the reloaded config and marks the summary stale; other watched files are logged at debug and ignored. A config change never starts a workspace scan on its own.
- Three custom requests. `nullscan/analyzeWorkspace` takes an optional `{ "folders": ["file:///..."] }`, defaults to every folder from `initialize`, and returns the same `summary` object as `--format json` via `nullscan_workspace::json::summary_json`. `nullscan/summary` returns `{ "summary": <object or null>, "stale": <bool> }` from the cache; the cache is marked stale by any `didOpen`/`didChange`/`didSave`/`didClose` and fresh again only after a successful scan. `nullscan/rules` ignores its params and returns `nullscan-lsp/src/rules.rs::catalog()`: one `{ id, title, description, why, severity, docs_url }` object per `nullscan_core::RULES` entry, in registry order, with `severity` lowercase (`error`/`warning`/`info`) and `docs_url` = `https://github.com/bytezer/nullscan/blob/main/RULES.md#<id>`. Custom requests need no initialization capability.
- Workspace scans never run on the dispatch loop: the worker owns a snapshot (folders, overrides, `AtomicBool`, sink clone) and answers through a `crossbeam-channel` job channel that the main loop `select!`s against client messages. Only one scan runs at a time (a second request fails with `RequestFailed`), `$/cancelRequest` sets that scan's flag, and only the dispatch thread applies the cache, publishes diagnostics and sends the `Response`.
- Each folder is scanned with its own `nullscan_workspace::config::load_in_dir` and merged with `nullscan_workspace::merge`; open buffers travel as `ScanOptions::overrides` so unsaved text wins. Published URIs are tracked, so a scan that no longer includes a file clears its diagnostics with an empty list (`version: None` for disk files).
- Multi-root: the server advertises `workspace.workspaceFolders` support and `changeNotifications`, keeps the folder list current from `workspace/didChangeWorkspaceFolders`, and marks the summary stale when the set changes.
- Config comes from each workspace folder's `nullscan.toml` via `nullscan_workspace::config::load_in_dir`; a broken file logs `window/logMessage` and falls back to defaults instead of failing the server.
- `--config <path>` (also `--config=<path>`) points the server at one explicit `nullscan.toml` for every open document and every scanned folder: `Server::config_for` and `requests::folder_config` call `nullscan_workspace::config::load(Some(path))` instead of `load_in_dir`, the disable-rule quick fix targets that file, a change to it republishes open documents, and a missing or broken file logs `window/logMessage` and falls back to the defaults. Unknown flags exit `2` with the usage line. The extension passes the flag when `nullscan.configPath` is set, resolving a relative path against the first workspace folder (`src/configPath.ts`) and warning at startup when the file does not exist.
- `nullscan_core::analyze()` (in `lib.rs`) parses once, builds one `FileContext { tree, source, config, scopes }`, and runs every enabled `RuleScope::File` entry from `RULES` in registry order. It builds the `ScopeGraph` only when at least one enabled file rule sets `requires_scope: true`, then passes it as `ctx.scopes`; otherwise that field is `None`. The public `analyze(source, language, config)` signature is unchanged. After collecting diagnostics, `suppression::apply` drops the ones covered by inline markers. TS and TSX share one rule set, so queries must be built with `tree.language()` rather than a hard-coded grammar.
- Cross-file `duplicate-code` is registered in `RULES` as `RuleScope::Project` with `run: None`; `nullscan-workspace::scan` orchestrates it with `find_duplicates` because it needs all sources. Rules needing whole-project context do not belong in `analyze()`.
- The SARIF catalog (`nullscan/src/sarif.rs`) and `rules.disabled` validation (`nullscan-workspace/src/config.rs`) both read `nullscan_core::RULES`; there is no duplicate metadata list in the CLI or workspace.
- Exit codes are `0` clean, `1` findings (diagnostics or duplicates), and `2` tool error (invalid config or no existing input path). `rayon` parallel maps collect in input order, so output order stays deterministic; preserve that when touching the workspace scan pipeline.
- `--format json` is the machine contract used by editors: `schemaVersion: 1`, tool/config/summary/diagnostics/duplicates/warnings sections, and a trailing newline. Diagnostic ranges use 0-based lines and 0-based UTF-16 characters; duplicate spans keep core's 1-based line numbers and each entry carries `lineCount`. `summary.duplication` adds `{ density, duplicatedLines, totalLines, duplicatedBlocks, duplicatedFiles, largestBlockLines }`. Warnings are part of the document, never stderr. Text prints duplicates as `file:line:column: [duplicate-code] duplicated block of N lines (T tokens), ...`; SARIF keeps its shape with `level` and the same message.

## Adding or changing a rule

- Add the implementation under `nullscan-core/src/lang/typescript/rules/` (one file per rule, `pub fn run(&FileContext<'_>) -> Vec<Diagnostic>`).
- Register it **exactly once** in `RULES` in `nullscan-core/src/rule.rs`, with its `RuleMeta` (id, description, title, why and severity), `RuleScope`, `requires_scope`, and runner:
  - file-scoped rules: `RuleScope::File`, `requires_scope: false`, and `run: Some(rules::<name>::run)`;
  - scope-dependent file rules: same, but `requires_scope: true`, and read `ctx.scopes` (returning early if it is `None`);
  - project-scoped rules: `RuleScope::Project`, `requires_scope: false`, and `run: None`, plus their own orchestrator.
- The registry is the only place the CLI reads rule IDs/descriptions from, so no `RULE_DESCRIPTIONS` update is needed (or possible) in the CLI.
- Add `nullscan-core/tests/fixtures/<rule-id>/valid.ts` (or `.tsx`) and `invalid.ts` (or `.tsx`). The fixture harness fails any file-scoped registry rule without a pair, so this is part of landing a rule, not optional cleanup. Use `.tsx` for at least one pair when the rule should be guarded under TSX.
- Add the rule's row to `RULES.md` (category, upstream equivalent, status) with `<a id="<rule-id>"></a>` as the first thing in the first cell. `every_rule_has_a_rules_md_anchor` in `nullscan-core/tests/rules.rs` fails without it, because the LSP builds docs links from `RULES.md#<rule-id>`.
- Inline suppressions and `[files].ignore` are generic: they apply to every file rule with no per-rule wiring. `[duplicates].ignore` only affects the project-scoped clone pass; `[duplicates].compare-markup` only toggles its token criterion.
- Entry order in `RULES` is the diagnostic-emission order for file rules. Existing tests assert exact rule vectors; insert a new rule where its diagnostics should appear rather than reordering existing ones.
- For a new threshold, add it to `nullscan_core::Config` defaults **and** `FileThresholdsConfig` in `nullscan-workspace/src/config.rs` (kebab-case `#[serde(rename = ...)]`). Non-threshold `[duplicates]` keys (currently `compare-markup`) live in `FileDuplicatesConfig` and are applied by `apply_duplicates`.
- Structural rules with a single `@report` capture should use the shared `query_rule` helper in `rules/query.rs`. Anything that inspects captured text or child counts needs a hand-written rule.
- **tree-sitter traps** (details and repros in `FINDINGS.md`):
  - `QueryCursor::matches` does not evaluate `#eq?`/`#match?`; filter `node.utf8_text(...)` in Rust.
  - Combining `operator:` with another field (`left:`/`right:`) silently matches nothing in this binding. Match the other field and read the operator text in Rust.
- Scope-dependent rules read the owned `ScopeGraph` in `scope.rs`; never store tree-sitter `Node` values in it. Scope unit tests (function vs block scoping, shadowing, hoisting, parameters, imports, destructuring, read/write counts, globals, loops/switches) live in `scope.rs`; update them when resolution changes.
- Reachability rules use `control_flow.rs` (and its unit tests) rather than building a CFG. `no-unused-collection` and `no-array-index-key` set `requires_scope: true`; the other dataflow rules are syntax-only by design.
- The Phase 5 security rules (`no-eval`, `no-implied-eval`, `no-new-func`, `no-script-url`, `hardcoded-secrets`) are syntax-only and deliberately avoid taint analysis, type information, and full dataflow. `hardcoded-secrets` is a name/value heuristic, not a secret scanner; see `RULES.md` for the full limitation list. The shared `static_string_text` helper in `rules/query.rs` recognizes `string` literals and substitution-free `template_string` nodes.
- Unit tests stay centrally in `nullscan-core/src/lang/typescript.rs` and assert exact rule vectors; cognitive complexity asserts exact scores. Registry sanity tests (unique IDs, non-empty descriptions/titles/whys, `duplicate-code`, stable ordering, `requires_scope`) live in `rule.rs`; the LSP catalog tests (52 entries, populated fields, `docs_url` anchor) live in `nullscan-lsp/src/rules.rs`. Fixture-based regression tests and the `RULES.md` anchor guard live in `nullscan-core/tests/rules.rs`. Update the relevant layer when behavior changes.

## CLI/file-walking notes

- Supported inputs: `.ts`, `.mts`, `.cts`, `.tsx`; JS is not supported.
- Directory walks (`nullscan-workspace/src/walk.rs`) skip dot-directories and `SKIPPED_DIRS` (`node_modules`, `dist`, `build`, `.next`, `out`) to avoid scanning generated output. Explicit unsupported files and missing paths become warnings; a run with no existing input path exits `2`.
- Default config is `./nullscan.toml` relative to the process CWD, not the target path. The loader lives in `nullscan-workspace/src/config.rs`; the resolved path is reported absolute in JSON. `[files].ignore` excludes paths from the whole run (explicit ignored inputs warn), `[duplicates].ignore` only removes them from clone detection, and `[duplicates].compare-markup` (default `false`) decides whether JSX markup counts as duplicate tokens; a wrong TOML type for either key is a config error.
